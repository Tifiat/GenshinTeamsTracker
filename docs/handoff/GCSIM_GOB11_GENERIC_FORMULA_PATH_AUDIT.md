## GP-2b ordered callback pilot: earlier partial checkpoint

Current implementation composes later changes to the numeric AttackInfo fields
`FlatDmg` and `BaseDmgBonus`, instead of treating their final observed value as
the entire formula. This extends the scalar pilot; it does not replace search.

- The source overlay follows a proven local `*info.AttackEvent` assertion inside
  an observed, uniquely bound event callback. It extracts scalar arithmetic
  from source and records actual executed field writes. It does not add any
  reaction/tag/character switch or implement a new game mechanic.
- Each write keeps its field, operation, before/after values, operand reference,
  execution order and callback occurrence. Compact compilation replays assign,
  add, subtract, multiply and divide in order. Assignment correctly discards
  old dependencies; multiplication is not approximated by an additive delta.
- Every callback net change must be covered by its write ledger. Predecessor,
  operand, per-write result and terminal values are checked. Missing/ambiguous
  writes freeze the field. An unknown operand can stay a local constant while
  a known incoming producer continues to respond to artifacts.
- Callback MaxHP/Stat getters retain the actual character owner and already
  executed modifiers. Each original getter is evaluated once. Artifact input
  remains a delta against the captured build; existing buffs are not added twice.
  Scope is this callback slice, not a claim of general typed getter discovery.
- Expression budgets are depth12/visits64. Unknown helpers, arrays and mutable
  operands retain explicit frozen evidence. Only same-file proven constants
  preserve literal semantics; unbound cases are not asserted independent.
  Local source constants keep their original numeric type instead of being
  defaulted to int by an instrumentation temporary. Unused local provenance
  does not prevent compilation if a subsequent unsupported branch is frozen.
- Internal `gtt_attack_field_writes_v1` metadata is in the live trace buffer,
  not legacy serialized hit JSON. `numeric_eval` now has typed
  `artifact_stat_read` and diagnosed `frozen_attack_operand` observations with
  strict owner/reference/incompleteness checks. Public compact IR is unchanged;
  old serialized captures cannot acquire these edges without recapturing.
  Preserve source/overlay/engine identity for reproduction. This does not claim
  legacy forensic readers accept every new internal observation operator.

## First missing links

1. **Direct reactions:** `pkg/enemy/damage.go::calcDirectReaction` already
   records the scaling stat/value, snapshot, EM, observed EM bonus, reaction
   bonus, crit and resistance/defense factors. But a structured expression
   recipe and the separate local `mult` provenance are not exported. The
   current consumer freezes this family. Do not infer `mult` by dividing two
   baseline numbers: zero inputs and state-dependent coefficients make that
   an unsafe substitute for provenance.
2. **Cloud:** upstream snapshots and modifies each contributing character,
   calls `CalcLunarReactionDmg`, rolls each crit, sorts realized contributions
   and sums them with positional weights. The queued attack receives the sum
   in `FlatDmg` and a nearly empty snapshot. Its final owner is the last
   trigger, not the owner of every stat. GTT observes the terminal number but
   has no contributor-group receipt; the producer calculation has no GTT
   trace hook. The data exists before aggregation, not in the final snapshot.
3. **Post-producer bonuses:** the upstream Lauma callback changes
   `AttackEvent.Info.FlatDmg` using her EM. GOB-11 fixed the resulting fatal
   validation mismatch, but still freezes affected channels. The missing
   piece is the ordered producer-plus-callback expression with source ownership.

## Generic compiler limits confirmed, not conjectured

`pkg/gttsourcegen/scan.go::describeSeamCall` discovers known API-shaped entry
points (queued attacks, modifier closures, health operations, events/tasks).
It is not an arbitrary recursive interpreter of every Go damage calculation.
`describeQueuedAttack` currently extracts an explicit `FlatDmg` initializer;
it does not reconstruct a whole mutable damage accumulator automatically.

Five probes call the actual `compileNumericTemplate` through a test-only
overlay. Results:

- `c.TotalATK()*1.5`: supported candidate-stat parameter.
- `snapshot.Stats[attributes.EM]`: **frozen source parameter**, yet marked
  dependency-complete by this syntax-only layer.
- `c.Stat(attributes.EM)`: `unsupported_call`.
- `combat.CalcLunarReactionDmg(...)`: `unsupported_call`.
- Renaming that call to `other.AnyNumericHelper(...)`: the same result.

The array-read result is a concrete unsafe generalization assumption: syntactic
purity does not prove artifact independence. This probe does not assert that
every occurrence is currently a wrong live score, or explain the entire 90%
by itself. It must be repaired before relying on generalized source slices.

Arithmetic depth is already bounded at 12, nodes at 64, forwarded attack calls
at 5. This failure is primarily missing dataflow/operator support, not merely
an overly small recursion budget. Keep bounded recursion/cycle checks.

## Recommended common route (design, not implemented)

Reuse the current expression graph, runtime observation and Go evaluator.
Do not add a second handwritten Lunar/Stellar formula registry. Extend the
existing machinery in bounded steps:

### GP-1: trustworthy numeric inputs

- Identify stat reads by proven engine types and runtime origin, including
  live `Stat` calls and snapshot-array access, not expression text alone.
- Bind each read to owner, stat, frame/snapshot identity and artifact-variable
  dependency. `Snapshot` currently carries no explicit character owner;
  preserve that binding at creation/transfer instead of guessing from the
  final damage owner. Some constructed snapshots have no single owner.
- Distinguish immutable talent/level tables from mutable stat arrays and
  state-indexed tables. Unknown provenance stays frozen/incomplete, never
  silently "independent" just because it is an array or exported field.

### GP-2: the common numeric calculation path

- Follow an observed terminal calculation to bounded arithmetic slices;
  support local scalar versions, pure helper arguments/returns and actual
  source constants/table values. Preserve operation order and runtime-selected
  branch evidence. Generate expression operations from upstream code, rather
  than hardcoding coefficients 3/1.6 or EM curves in the consumer.
- Export the executed local multiplier with its source/condition. Known state
  dependencies remain variable; unresolved state is a local frozen boundary.
- Compose later additions/multiplications into the same expression, retaining
  the original producer and callback owners. Do not replace the entire
  producer receipt with only the final flat number.
- No need to interpret the complete rotation or arbitrary Go. Unsupported
  calls, aliasing or control flow retain observed values and diagnostics. A
  source rewrite must preserve single evaluation, RNG order and trace-off DPS.

Start validation with the two observed direct-reaction paths: their current
damage shares make them the highest-value pilot. The existing Stellar branch
is a structural cross-check, not an assertion of completed gameplay testing.

### GP-3: contributor collections

2026-09-16: implemented and installed after bounded12-point response acceptance.
Contributor receipts lower conditional expectation to neutral arithmetic IR.
Saved-vector/captured-scalar ancestry closes the shared-EM reaction-bonus loss.
No new gameplay operator/formula copy. Full search still needs its own gate.
Current evidence/limits: GCSIM_GOB11_GP3_CHECKPOINT.md.

- Preserve each contributor expression and owner before flattening. Represent
  the observed sort/reduction as a generic ordered weighted aggregation whose
  weights and tie behavior come from upstream. Do not assign all inputs to
  the last trigger and do not fix contributor order to the original build.
- Expected crit must precede expectation of the whole nonlinear aggregation,
  not be naively averaged before sorting. A candidate bounded method is exact
  enumeration of independent per-contributor crit states: at most 16 for four
  contributors, reusing their pre-crit expressions. This is offline arithmetic,
  not 16 simulations or artifact enumeration. It requires proof of independence
  and a fixed applicable event/contributor context; more complex random or
  topology dependencies retain an explicit boundary and budget.
- The user accepted this bounded collection/expectation direction. Keep its
  limits explicit; only a new conceptual issue needs another discussion.
  Existing scalar add/multiply/min/max/power operations alone do not encode the
  general contributor collection contract.

### GP-4: acceptance and update resilience

- First synthetic inputs with arbitrary names, then the existing Flins and
  bloom fixtures: baseline AND controlled stat-response checks, including
  all actual contributing owners, crit, EM and absent DMG% multiplication.
- Check the existing Chasca graph, producer/buff composition and bounded
  candidate ranking. Do not claim full search success from formula parity only.
- Version the changed evidence/compiler contracts and repeat clean patch,
  build, semantic smoke and rollback gates. Keep package/type/API integration
  mappings separate from source-derived mathematical expressions.
- New mechanics using supported operations may work without reaction-specific
  changes; arbitrary future Go behavior cannot be guaranteed to decompose.
  Unknown paths must remain diagnosable and must not poison known regions.
